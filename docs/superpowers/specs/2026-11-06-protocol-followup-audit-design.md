# 求援补证审计链设计

日期：2026-11-06
状态：已确认采用方案 A，待书面规格复核
项目：千界花园／协议求援与活性证据补证

## 1. 目标

在不改变现有证据等级和求援核销语义的前提下，将以下材料绑定为可重放、不可覆盖的审计记录：

- 调用方显式选择的求援基线；
- 当前请求中与核销计算有关的最小快照；
- 确定性求援与核销结果；
- 算法版本和源代码版本；
- 可选的三角色模型复核记录及其真实结束状态。

审计链回答的问题是：**哪一份基线，在哪一份证据快照上，由哪一版算法，产生了哪些未决、已核销和待复核求援？**

## 2. 已确认的方案与边界

采用“显式基线＋内容寻址的追加式审计束”。

不采用自动最新快照，因为最新快照可能来自不同算法版本或不同证据状态。当前不迁移为完整事件溯源系统；现有求援快照继续兼容，新审计束提供重放能力。

以下边界不可削弱：

- 核销不等于实验真实、独立、可复现或理论成立。
- 模型复核只有提出问题和建议的权限，不能核销求援、修改 `methodStatus`、改写证据或提升证据等级。
- `complete` 只表示要求的模型角色均正常结束，不表示其内容正确。
- 原文、方法和冲突求援不会因从当前列表中消失而自动核销。
- 活性上下文只可由同一证据或显式派生的 primary／verified full_text／protocol 中的实际引用核销。
- 所有审计和复核产物始终保持 `evidenceUpgrade=false`。

## 3. 非目标

本阶段不做以下事项：

- 不自动选择“最新”或“最佳”基线；
- 不根据模型文本自动接受、拒绝或修改证据；
- 不自动修正既有文献的 `methodStatus`、文档身份或来源角色；
- 不实现完整事件溯源、数据库迁移或前端看板；
- 不把模型复核文本解析为机器可执行结论；
- 不默认发起付费模型调用；
- 不直接推送 `main`，不触发部署。

## 4. 组件划分

### 4.1 `protocol-followup-audit.ts`

纯确定性审计模块，负责：

- 生成计算所需的最小请求快照；
- 规范化 JSON 并计算审计键；
- 生成审计束；
- 校验既有审计束；
- 从审计束重放核销结果；
- 比较当前请求与历史快照是否漂移。

该模块不调用模型，不读取密钥，不启动 Next.js 服务。

### 4.2 `protocol-followup-audit-store.ts`

本地追加式存储，负责：

- 将审计目录限制在项目内的相对目录；
- 将基线路径限制在 `data/protocol-followups/` 内的 JSON 文件；
- 使用内容寻址文件名和原子写入；
- 相同输入重复运行时返回已有记录，不重写文件；
- 已存在文件无效、被篡改或与内容寻址冲突时拒绝覆盖；
- 在写入前进行密钥模式检查，命中时拒绝写入而不是静默改写证据。

测试通过 `PROTOCOL_FOLLOWUP_AUDIT_DIR` 指定项目内临时目录。默认目录为 `data/protocol-followup-audits/`。测试产物不进入提交。

### 4.3 `tools/run-protocol-followup-audit.mjs`

显式命令行入口，负责：

- 接收 `--request-id` 和 `--baseline <path>`；
- 读取当前协议请求和显式基线；
- 调用确定性审计生成与本地存储；
- 输出审计键、记录路径、未决数、核销数和待复核数；
- 支持 `--verify <audit-path>` 重放既有审计束；
- 支持 `--check-current <audit-path>` 报告当前请求是否相对历史快照漂移。

审计生成不调用模型。路径逃逸、跨请求基线、重复基线指纹和无效输入均在写盘前失败；本工具本身不发起模型调用。

### 4.4 `tools/run-protocol-followup-review.mjs`

独立、显式执行的模型复核入口，负责：

- 读取已存在的审计束及其 `auditKey`；
- 使用现有 `researchChat` 通道执行三角色复核；
- 保存真实 provider、model、finishReason、usage、latencyMs、原始意见或脱敏错误；
- 将复核记录写入新文件，绝不修改原审计束或历史复核文件；
- 正常结束、截断、失败和部分完成均保留原状。

模型复核不是审计重放的一部分，不能改变确定性结果。

## 5. 数据流

```text
显式基线 JSON
       │
       ├── 校验路径、requestId、求援指纹及重复项
       │
当前 ProtocolRequest
       │
       ├── 生成最小计算快照，剔除联系人、回执、工作项和既有评论
       │
       ▼
reconcileProtocolFollowups
       │
       ▼
审计键＋不可覆盖审计束
       │
       ├── 确定性重放／当前证据漂移检查
       │
       └── 可选三角色复核 → 独立追加式复核记录
```

审计生成失败时不调用模型。复核失败不删除或修改已存在的确定性审计束。

## 6. 最小请求快照

审计束保存核销计算所需的请求数据，包括请求 ID、标题、场景、状态、文档、证据、来源引用和时间戳。

以下字段不进入快照：

- `contacts`：避免复制不必要的联系人信息；
- `receipts`：发送回执不参与上下文核销；
- `workItems`：界面工作状态不参与确定性核销；
- `reviews`：历史模型意见不参与确定性核销。

快照使用与 `ProtocolRequest` 兼容的结构，上述列表字段保存为空数组，可选评论字段省略。这样可直接调用现有核销函数，同时避免扩大个人信息和模型意见的暴露面。

## 7. 审计键与规范序列化

审计键为完整 SHA-256 十六进制字符串，计算输入为 UTF-8 规范 JSON：

```json
{
  "schemaVersion": "protocol-followup-audit/v1",
  "algorithmVersion": "protocol-followup-reconciliation/v1",
  "requestId": "...",
  "baseline": {},
  "requestSnapshot": {}
}
```

规范序列化规则：

- 对象键按 Unicode 码点排序；
- 数组顺序保持不变；
- 不省略或修改基线、证据和活性记录中的有效字段；
- `undefined` 属性不进入 JSON，与现有持久化行为一致；
- 审计记录自身的 `createdAt` 不参与审计键；
- 基线自身的 `generatedAt` 是精确输入的一部分，不擅自删除；
- 算法版本参与审计键，源代码版本仅作溯源元数据。

审计文件名为：

```text
<requestId>-<完整 auditKey>.json
```

完整哈希用于文件名，避免短哈希碰撞造成不同输入共用路径。

## 8. 审计束结构

审计束至少包含：

```text
schemaVersion
algorithmVersion
auditKey
requestId
createdAt
sourceRevision（可获得时）
inputs
  baselinePath（项目内相对路径）
  baseline（精确对象）
  requestSnapshot（最小计算快照）
deterministicResult（包含核销和 reconciliation）
evidenceUpgrade=false
boundaries
```

`deterministicResult.generatedAt` 是结果生成时间，重放比较时仅在结果根节点排除该字段。其他时间、数值、单位、来源、比较符和证据字段均参与比较。

审计束不保存环境变量、API 密钥或模型请求头。模型复核记录也不保存这些内容。

## 9. 幂等、不可覆盖与原子写入

- 写入前先计算完整审计键和目标路径。
- 目标不存在时，先以排他方式创建同目录临时文件，写入并 fsync；再通过排他硬链接发布目标，成功后删除临时文件。目标已存在时发布失败并进入既有记录验证，绝不覆盖。
- 目标已存在时，读取并验证其审计键、输入和确定性结果；一致则直接返回已有记录，不改变文件内容或修改时间。
- 目标已存在但 JSON 无效、哈希不符、输入不符或重放结果不符时，返回冲突错误，不覆盖。
- 不用随机文件名规避冲突，不自动生成 v2、v3 来掩盖同一内容寻址记录的篡改。
- 不同精确输入自然产生不同审计键和新文件。

Windows 文件锁导致的暂时性失败只在既有有界重试策略内处理，不进行紧密循环重试。

## 10. 重放与漂移检查

重放只使用审计束内的基线和请求快照：

1. 重新计算审计键并核对；
2. 调用同一算法版本的核销函数；
3. 排除结果根节点的 `generatedAt` 后规范序列化；
4. 与保存的确定性结果逐字段比较。

算法版本不支持时明确失败，不静默使用新版本重放旧记录。

漂移检查额外读取当前协议请求，生成相同规则的最小快照，并与审计束快照比较。结果仅为：

- `unchanged`：计算相关输入相同；
- `drifted`：计算相关输入不同，同时返回当前快照哈希和记录快照哈希。

漂移检查不更新旧审计束，不自动产生新核销结论。

## 11. 模型复核记录

复核记录采用独立文件：

```text
<完整 auditKey>-review-<attempt>.json
```

记录至少包含：

- `schemaVersion=protocol-followup-review/v1`；
- `auditKey`；
- `generatedAt`；
- `status=complete|partial`；
- 每个角色的 provider、model、finishReason、usage、latencyMs、content 或脱敏 error；
- `evidenceUpgrade=false`。

`attempt` 只用于区分不同复核运行，不参与审计键。已有复核文件不可覆盖。只有全部角色真实完成且结束状态属于现有允许集合时才为 `complete`；空意见、截断、未知结束状态、调用失败或部分角色失败均为 `partial`。

模型角色和模型选择沿用现有三角色配置。复核输入仅包含审计束中的确定性结果和最小请求快照，不读取联系人、回执或环境变量内容作为提示词。

## 12. 错误与安全处理

- 请求 ID 继续沿用现有安全格式校验。
- 基线必须为指定目录内的 JSON 文件，拒绝绝对路径、`..`、目录穿越和非 JSON 输入。
- 基线 `requestId` 必须与当前请求一致。
- 审计目录必须为项目内相对目录，禁止绝对路径和 `..`。
- 写入前扫描序列化产物中的已知密钥模式；命中时拒绝写入并给出不含秘密的错误。
- 模型错误使用现有脱敏方式，不打印环境变量，不在日志中复述密钥。
- 不保留临时 Next.js 服务，不修改原始证据和历史求援快照。

## 13. 测试策略

严格按测试先行实现，先观察功能缺失导致的失败，再写生产代码。

### 确定性单元测试

1. 相同精确输入产生相同审计键，审计记录时间不影响审计键。
2. 不同基线、证据快照或算法版本产生不同审计键。
3. 最小快照不含联系人、回执、工作项和既有评论，核销结果与原始请求一致。
4. 相同输入重复保存返回原记录，文件内容和修改时间不变。
5. 无效、篡改或冲突的已有文件被拒绝且不覆盖。
6. 重放排除结果根节点时间戳后完全一致。
7. 非结果根节点的证据时间或原始值变化会导致重放失败。
8. 漂移检查只报告 `unchanged` 或 `drifted`，不写文件。
9. 路径逃逸、跨请求基线、重复基线指纹、未知算法版本和密钥模式均被拒绝。
10. 审计生成和重放不修改输入对象，`evidenceUpgrade=false`。

### 复核状态测试

- 全角色正常结束才为 `complete`。
- 空意见、截断、未知结束状态、任一失败均为 `partial`。
- 复核文件引用正确 `auditKey`，不含秘密，不改变确定性审计束。

### 项目回归

完成后运行全部 Node／协议测试、项目单测、TypeScript、ESLint、生产构建和协议端到端场景。若新增 HTTP 路由则更新操作目录；本设计优先复用现有核销路由和本地工具，不默认新增路由。

## 14. 完成标准

本阶段只有在以下条件全部满足后才算完成：

- 给定基线和最小请求快照，可以生成内容寻址的不可覆盖审计束；
- 同一审计束可以按声明算法版本重放并得到一致结果；
- 当前证据漂移可以检测且不会改写历史；
- 可选三角色复核与精确审计键绑定，真实结束状态完整保留；
- 模型意见不能改变求援或证据状态；
- 全部边界测试和项目回归通过；
- 研究分支精确提交并推送，临时文件、密钥和个人扩展数据不进入提交。
