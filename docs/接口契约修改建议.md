# 接口契约修改建议

> 分析日期：2026-05-26
> 分析对象：《后端前端接口契约.md》+ 附录D（18 API分组 / 60+ REST端点）
> 对比基准：本地 `sylva_platform/backend/src/routes/` 35+ 路由文件实际代码

---

## 一、核心结论：接口契约设计完善，但存在5类问题

1. **mock数据 vs 真实实现**：7个核心路由仍为mock，需明确接入计划
2. **端点命名不一致**：同一功能存在多个命名风格
3. **类型定义分散**：TS类型分布在多个文件，未统一
4. **平台生态API过度设计**：部分API对应的功能尚未实现
5. **缺少安装要求/配置状态查询**：用户无法知道某个平台是否可用

---

## 二、具体问题与修改建议

### 2.1 问题：核心路由仍为mock数据

**现状**：

| 路由文件 | 大小 | 状态 | 说明 |
|---------|------|------|------|
| `coordinator.ts` | 19KB | ⚠️ mock | 待接入 `CoordinatorHierarchy.ts` |
| `handoff.ts` | 7KB | ⚠️ mock | 待接入 `InterChariotHandoffProtocol.ts` |
| `hierarchical.ts` | 16KB | ⚠️ mock | 待接入层级协调 |

**建议修改**：

1. 在接口契约中明确标注这些端点的 **实现状态**：
```typescript
// 建议在每个路由的JSDoc中标注
/**
 * @status mock        // mock | implemented | deprecated
 * @targetModule CoordinatorHierarchy.ts
 * @plannedDate 2026-06-01
 * @blockingIssue 等待CoordinatorHierarchy.ts完成单元测试
 */
```

2. 添加 **「实现状态查询」端点**，让前端可以知道哪些功能可用：
```
GET /api/system/capabilities
```
返回：
```typescript
interface SystemCapabilities {
  version: string;
  features: Array<{
    name: string;
    status: 'stable' | 'beta' | 'mock' | 'disabled';
    endpoints: string[];
    since?: string;
  }>;
  providers: Array<{
    id: string;
    status: 'active' | 'beta' | 'unconfigured';
    configured: boolean;  // API Key是否已配置
  }>;
  tools: Array<{
    id: string;
    installed: boolean;
    installable: boolean;
  }>;
}
```

### 2.2 问题：端点命名风格不一致

**现状**：同一类功能存在多种命名风格

| 功能 | 现有端点 | 问题 |
|------|---------|------|
| Agent管理 | `/api/agents` + `/api/agentsV2` + `/api/agents/runtime` | 版本号在URL中，不是RESTful |
| 干预请求 | `/api/intervention/request` + `/api/intervention/global-pause` | 混合了资源名和动词 |
| 工作空间 | `/api/workspace/:groupId` vs `/api/workspaces` | 单复数不一致 |
| 统一API | `/api/unified-api/*` vs `/api/unified/*` | 两个前缀并存 |

**建议修改**：

1. **统一采用RESTful资源命名**：
```
# 修改前（不一致）
GET /api/agentsV2
GET /api/agents/runtime
POST /api/intervention/request
POST /api/intervention/global-pause

# 修改后（统一）
GET /api/v2/agents          # 版本号放前缀
GET /api/v2/agents/:id/status
POST /api/interventions      # 资源名复数
POST /api/interventions/global-pause  # 子资源
```

2. **统一工作空间端点**：
```
# 修改前
POST /api/workspace/:groupId
GET /api/workspaces

# 修改后
POST /api/workspaces/group/:groupId  # 明确是group下的workspace
GET /api/workspaces
GET /api/workspaces/:id
```

3. **统一统一API端点**（消除`unified-api`和`unified`的重复）：
```
# 修改前
/api/unified-api/config
/api/unified-api/detect
/api/unified/chat

# 修改后
/api/v1/unified/config
/api/v1/unified/detect
/api/v1/unified/chat        # 去掉-api后缀，unified本身就包含api含义
/api/v1/unified/chat/stream
```

### 2.3 问题：类型定义分散，未统一出口

**现状**：
- TS类型定义散落在 `backend/src/routes/`、`backend/src/services/`、`frontend/src/shared/types/`
- 接口契约中的类型（如 `HierarchyReport`、`Blueprint`、`InterventionRequest`）是文档中的示例，不是真实代码中的类型
- 前端和后端可能使用不同的类型定义

**建议修改**：

1. **建立统一的类型包**：
```
sylva_platform/
├── packages/
│   └── types/              # 新建：统一类型包
│       ├── src/
│       │   ├── api.ts      # 所有API请求/响应类型
│       │   ├── models.ts   # 数据模型类型
│       │   ├── provider.ts # Provider相关类型
│       │   └── index.ts    # 统一出口
│       └── package.json
```

2. **接口契约中的类型必须与代码同步**：
```typescript
// 当前契约中的示例（可能与代码不符）
interface ChatMessage {
  role: 'system' | 'user' | 'assistant' | 'tool';
  content: string;
}

// 代码中实际的类型（ProviderAdapters.ts）
export interface ChatMessage {
  role: 'system' | 'user' | 'assistant' | 'tool';
  content: string;
  name?: string;  // 代码中有name字段，契约中没提到
}
```

3. **类型版本控制**：
```typescript
// 在类型文件中标注版本
/**
 * @apiVersion 1.2.0
 * @lastModified 2026-05-25
 * @breakingChanges none since 1.1.0
 */
export interface AgentConfig {
  // ...
}
```

### 2.7 问题：Blueprint数据模型缺少执行上下文

**现状**：
```typescript
interface BlueprintNode {
  id: string;
  type: 'agent' | 'group' | 'coordinator' | 'frontend' | 'backend' | 'tool' | 'protocol';
  presetId?: string;
  groupId?: string;
  position: { x: number; y: number };
  configOverrides?: Record<string, any>;
  entrypoint?: boolean;
}
```

**问题**：
- `type: 'frontend' | 'backend' | 'tool'` 将外部平台作为节点类型，但Blueprint是千界花园内部的工作流
- 这些外部平台无法作为Blueprint的"节点"来执行
- 应该改为"通过Provider调用外部API"或"通过工具调用外部CLI"

**建议修改**：

```typescript
interface BlueprintNode {
  id: string;
  type: 'agent' | 'group' | 'coordinator' | 'tool_call' | 'api_call' | 'conditional' | 'loop';
  
  // 千界花园内部资源引用
  presetId?: string;           // Agent预设
  groupId?: string;           // 群组引用
  
  // 外部调用（统一为两种）
  toolCall?: {                // 调用Z轴工具（CLI/MCP）
    toolId: string;           // 如 'claude-code', 'codex'
    command: string;
    args?: string[];
  };
  
  apiCall?: {                 // 调用Y轴Provider API
    providerId: string;       // 如 'openai', 'ollama'
    modelId?: string;
    promptTemplate?: string;
  };
  
  position: { x: number; y: number };
  configOverrides?: Record<string, any>;
  entrypoint?: boolean;
}
```

### 2.8 问题：InterventionTargetType过于宽泛

**现状**：
```typescript
targetType: "group" | "agent" | "coordinator" | "frontend" | "backend" | "tool" | "bridge"
```

**问题**：
- `frontend`、`backend`、`tool` 作为干预目标没有意义
- 干预系统是针对千界花园内部运行态的操作，外部平台不在千界花园的运行时内
- 干预"一个外部前端"或"一个后端推理引擎"不是千界花园的职责

**建议修改**：

```typescript
targetType: "group" | "agent" | "coordinator" | "blueprint" | "bridge"

// 移除：frontend, backend, tool
// 理由：干预系统只管理千界花园内部的运行时实体
// 外部平台的干预应通过其自身的管理接口
```

如果需要管理外部平台的启停，应该通过专门的API：
```
POST /api/backends/:id/stop     // 这是后端引擎管理，不是干预系统
POST /api/tools/:id/uninstall   // 这是工具管理，不是干预系统
```

  agentIds: string[];

## 三、优先级排序

| 优先级 | 修改项 | 影响 | 工作量 |
|--------|--------|------|--------|
| P0 | 实现状态查询端点 (`/api/system/capabilities`) | 前端需要知道哪些功能可用 | 小 |
| P0 | Provider状态查询 (`/api/providers/status`) | 用户需要知道Provider是否配置 | 中 |
| P0 | 统一端点命名风格 | API一致性 | 中 |
| P1 | 建立统一类型包 | 前后端类型同步 | 中 |
| P1 | 标记规划API为「未实现」 | 避免过度承诺 | 小 |
| P1 | Blueprint节点类型修正 | 数据模型正确性 | 中 |
| P2 | 批量操作端点 | 用户体验 | 中 |
| P2 | 补充错误码 | 调试效率 | 小 |
| P2 | 工具状态查询 | 安装管理 | 中 |
| P3 | InterventionTargetType精简 | 语义清晰 | 小 |

## 四、补充建议：新增「环境检查」端点

建议新增一个端点，让前端可以一键检查整个千界花园的运行环境：

```
GET /api/system/environment
```
返回：
```typescript
interface SystemEnvironment {
  version: string;
  node: { installed: boolean; version: string };
  python: { installed: boolean; version: string };
  docker: { installed: boolean; version?: string };
  ollama: { installed: boolean; running: boolean; models: string[] };
  gpu: { available: boolean; vendor?: string; vram?: number };
  
  // 千界花园组件状态
  components: {
    backend: 'running' | 'stopped' | 'error';
    frontend: 'running' | 'stopped' | 'error';
    agentZero: 'running' | 'stopped' | 'not-installed';
    database: 'connected' | 'disconnected';
  };
  
  // Provider配置概览
  providers: {
    total: number;
    configured: number;
    healthy: number;
    list: Array<{ id: string; configured: boolean; healthy: boolean }>;
  };
  
  // 工具安装概览
  tools: {
    total: number;
    installed: number;
    list: Array<{ id: string; installed: boolean }>;
  };
}
```

这个端点可以让用户在Dashboard上一眼看到：
- 哪些Provider已配置且健康
- 哪些工具已安装
- 本地环境是否就绪
- 哪些功能因为缺少依赖而不可用
